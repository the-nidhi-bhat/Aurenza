# Aurenza

The Null Theory First Project — an explainable produce allocation and dispatch
planning engine for perishable fruits and vegetables.

Aurenza compares a deterministic **FEFO baseline** against an optimizing
**planner**, allocating harvested inventory to feasible retail/wholesale
destinations while respecting shelf life, demand, capacity, transport and
handling costs, discounts, and disruptions — and explains every dispatch.

> Governing reference: [`docs/CONTRACT.md`](docs/CONTRACT.md) **v1.0.0-draft.4**
> (status: PROPOSED — NOT FROZEN). Assumptions and clarifications live in
> [`docs/ASSUMPTIONS.md`](docs/ASSUMPTIONS.md).

## Quick start

Requires **Python 3.11+**. No third-party runtime dependencies (standard library
only); `pytest` is used for tests.

```powershell
# 1. Run the test suite
python -m pytest -q

# 2. Generate the committed demo output (baseline vs planner, one scenario)
python -m engine.scripts.run_plan --seed 1

# 3. Regenerate the multi-seed evaluation summary
python -m engine.scripts.run_eval

# 4. Open the dashboard (serves the repo root; no front-end build or deps)
python dashboard/serve.py
# then open the printed URL, e.g. http://127.0.0.1:8000/dashboard/
```

Outputs:

- `demo/result.json` — one generated demo scenario, both strategies (committed fixture).
- `demo/evaluation.json` — 120 scenarios (`standard` mode), aggregate stats (committed
  generated fixture; regenerate with `python -m engine.scripts.run_eval --out demo/evaluation.json`).
- `output/<scenario_id>/result.json` — same, per-scenario (gitignored, regenerable); add `--also-output`.
- `output/evaluation.json` — same as `demo/evaluation.json` (gitignored).

These files are **generated by the real engine** — they are synthetic demo data, not
observed real-world performance.

## Run the dashboard

A small, dependency-free dashboard reads the generated JSON — it imports **no
engine code** (contract §10), so it shows exactly what the engine produced.

```powershell
python dashboard/serve.py          # serves the repo root on 127.0.0.1:8000
# open http://127.0.0.1:8000/            (landing page)
#      http://127.0.0.1:8000/dashboard/  (console — asks you to sign in first)
```

- **Decision detail** — baseline vs planner KPI cards (net revenue, spoilage kg,
  demand fulfillment), both dispatch tables with quantities, destinations,
  discounts and per-dispatch reasons, a batch overview, and the accounting
  reconciliation check.
- **Evaluation across scenarios** — aggregate across all 120 `standard` runs
  (revenue / spoilage / fulfillment win counts), plus a per-scenario selector.

It reads `demo/result.json` and (if present) `demo/evaluation.json`. If the
evaluation fixture is absent it shows the single demo scenario only.

`python -m pytest -q` also covers the dashboard (`dashboard/test_dashboard.py`),
including a test that starts the real server and asserts the pages and JSON load.

## What it does

For a scenario (available batches × candidate destinations + cost model +
optional disruptions) the engine produces, for **both** strategies:

- an allocation/dispatch plan (`dispatches`),
- metrics (revenue, costs, quantities, fulfillment, feasibility),
- per-batch summary, and
- a self-checking reconciliation block,

then an `improvement` block comparing planner vs baseline.

### Baseline — deterministic FEFO heuristic
- Batches are ordered by **earliest expiry** (`harvest_day + shelf_life_days`, then `batch_id`).
- Each batch is routed to the feasible destination with the **highest effective price** (then `destination_id`).
- Discounts are **not** applied.
- The baseline **obeys every hard constraint** the planner does. It is a credible
  heuristic floor, not a deliberately weakened strawman.

### Planner — bounded deterministic heuristic
- Considers every (batch × destination) edge, including the smallest 5%-grid
  discount that unblocks a destination's `max_price_per_kg` cap.
- Ranks edges by per-kg gain and allocates greedily under all hard constraints.
- Skips any edge whose gain is non-positive (shipping would destroy value).
- **Warm-starts** from the baseline plan: it never returns a plan worse than the
  baseline's objective.
- This is a **bounded heuristic, not proven globally optimal**. It does not run an
  unbounded combinatorial search.

### Objective & tie-breakers (§5.4)
Maximize `net_revenue`. Ties (within ₹0.01) are broken by lower `spoiled_kg`, then
higher `fulfillment_pct`, then deterministic id/expiry order.

## Cost & accounting model

Per dispatch (§5.1/§5.2), all money in ₹/kg:

```
effective_price   = price_per_kg[produce] × (1 − discount_pct/100)
gross_revenue     = sold_kg × effective_price
procurement_cost  = sold_kg × unit_cost_per_kg            # COGS, sold kg only
transport_cost    = quantity_kg × distance_km × transport_per_kg_km
handling_cost     = quantity_kg × handling_per_kg
expected_contribution = gross_revenue − procurement_cost − transport_cost − handling_cost
```

Aggregate (§5.3) — spoilage subtracted **once**:

```
net_revenue = Σ expected_contribution − spoilage_cost
spoilage_cost = Σ spoiled_kg × penalty   # cost_model.spoilage_penalty_per_kg if given, else batch unit_cost_per_kg
```

`spoiled_kg` (a quantity) and `spoilage_cost` (money) are kept strictly separate.
The internal `selection_score` is never included in financial aggregates.

### Reconciliation precision
Internal reconciliation uses **unrounded** values within the contract's ₹0.01
tolerance; presentation amounts are rounded to 2 dp only afterward. Because each
output field is rounded independently, the sum of rounded fields can differ from
the rounded total by a few paise — the authoritative check is the unrounded
identity, reported as `reconciliation.check_ok`.

## Constraints enforced (§11)

Violations are collected in `metrics.violations` with `feasible == false` when any
occur. Implemented and tested codes:

`unknown_disruption_type`, `negative_quantity`, `inventory_exceeded`,
`capacity_exceeded`, `demand_exceeded`, `shelf_life_expired`,
`arrival_after_horizon`, `discount_out_of_range`, `discount_step_mismatch`,
`invalid_near_expiry_days`, `unsupported_destination_type`, `unknown_reference`,
`cost_reconciliation_failed`.

`inventory_not_conserved` is structurally guaranteed by the §1.4 terminal-state
split (every batch's `harvested_kg` is partitioned into sold / fresh / spoiled by
construction), so it cannot fire for valid inputs.

## Assumptions, limitations, troubleshooting

See [`docs/ASSUMPTIONS.md`](docs/ASSUMPTIONS.md) for the full ledger. Highlights:

- **Synthetic data only.** `engine/fixtures.py` is clearly labelled demo data.
  Real prices/demand await the A9 produce catalogue (owner: Iffa).
- **Disruption effects are provisional** (contract names the types but not their
  parameters).
- **`notes="no_demand"`** is required by §6.3 but absent from the §8 schema; the
  engine omits it to stay schema-exact (CLARIFICATION-1).
- **Baseline is undefined by the contract**; FEFO is a team decision.
- With the mandated FEFO baseline (which already dispatches expiring stock first),
  spoilage reduction is typically 0 — the planner's measurable gain is net revenue.
  This is an honest property of a strong baseline, not a missing feature.
- **Destination price caps (§2.5).** A capped destination buys only while its
  effective price is within `max_price_per_kg`; an unsellable dispatch is dropped
  and does not consume the demand budget or book revenue.
- **Discounts are near-expiry only (§2.3).** A capped destination is served at
  full price when the decayed effective price already fits the cap; otherwise the
  smallest discount-grid step that meets the cap is used, and only for a
  near-expiry batch. The standard fixture contains no such opportunity, so its
  discounts are zero; the policy is covered by dedicated unit and end-to-end tests.

Troubleshooting:

- `ModuleNotFoundError: engine` — run commands from the repository root.
- Unicode console errors (`Σ`, `−`, `₹`) on Windows cp1252 — the engine writes
  UTF-8 files; only some consoles fail to *print* those glyphs.
- Stale outputs — delete `output/` and re-run `run_plan` / `run_eval`; `demo/result.json`
  is regenerated by `run_plan`.

## Status

Engine, baseline, planner, metrics, constraints, demo and evaluation outputs, and
the dashboard are implemented and covered by `python -m pytest -q` (**76 tests**:
67 engine + 9 dashboard). Destination price caps are enforced end-to-end with the
same rule in the baseline, the planner and `build_dispatches` (§2.5), and
discounts are offered only for near-expiry batches (§2.3). The planner applies the
§5.4 objective with ties broken by lower spoilage then higher fulfillment; on the
current synthetic fixtures the honest reported gain is net revenue (**+22.76%**
aggregate, never worse: 115/120 wins, 24/120 on all three metrics), while spoilage
is tied in 118/120 runs and fulfillment is lower in 91/120. Outstanding external
input: the A9 produce catalogue (see `docs/ASSUMPTIONS.md` §4).
